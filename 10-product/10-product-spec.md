# 10 — SSP Product Specification

The Self-Service Platform (SSP) lets an application team order cloud resources the way they would order from a store, and guarantees that what is delivered meets every enterprise guardrail. It replaces Taxi. This document is the functional contract; the API, workflow, policy, catalog and UI specs refine it.

## 1. Personas

| Persona | Who | Can | Cannot |
|---|---|---|---|
| **Buyer** | Developer or app team member entitled to one or more APM IDs | Browse catalog, configure and place orders for entitled tenant boundaries, view status, view equivalent code, change or decommission resources their APM owns, chat with Sidekick | See other APMs' resources; override guardrails; touch platform settings |
| **App owner** | Accountable owner of an APM ID | Everything a buyer can, plus sign off on orders flagged `owner_signoff` (e.g., production deletes), manage buyer entitlements for the APM | Operate the platform |
| **Platform operator** | Platform team | Control room: fleet status, pause/resume, retry runs, drift triage, module rollout waves, catalog publication, operator chat | Place orders on behalf of tenants in production (self-service only, D-15) |
| **Security reviewer** | Security engineering | Policy bundles, policy-impact review, T3 approvals, audit views | Operate workflows |
| **Auditor** | Compliance | Read-only across orders, approvals, runs, evidence | Anything else |

Entitlements: SSP-PROD-001 Buyers are entitled through APM ownership records (source: enterprise portfolio / ServiceNow; POC: `entitlements.yaml` in the control plane). SSP-PROD-002 A buyer sees only tenant boundaries whose APM IDs they are entitled to. SSP-PROD-003 Entitlement is evaluated on every API call, never cached in the UI as authority.

## 2. The four states

```
            POST /orders            policy + guardrails            render + plan + apply            refresh + post-build
 Buyer ───────────────► REQUESTED ─────────────────────► APPROVED ─────────────────────► EXPECTED ──────────────────► OBSERVED
                            │                                │                                 │                           │
                            │ rejected (policy deny,         │ cancelled (buyer, before run)   │ failed (run error) ──► retry / escalate
                            │ invalid, not entitled)         │ needs CR / owner sign-off ──► waits, then continues        │
                            ▼                                ▼                                 ▼                           ▼
                         REJECTED                        CANCELLED                        FAILED                 drift detected → DRIFTED (sub-state of Observed)
```

| State | Stored in | Produced by | Contains |
|---|---|---|---|
| Requested | Postgres `orders` | API on `POST /v1/orders` | Buyer identity, service id + version, tenant boundary, requested parameters (schema-valid), preview hash, idempotency key |
| Approved | Postgres `approved_specs` | Approval workflow | Immutable merged parameters (requested + injected guardrails), policy decision record, price estimate, change-management reference (CR id) if any, approved-by (system or human), hash |
| Expected | GCS LOB bucket `…/<tenant>/expected/` + Postgres pointer | Reconciler workflow | Rendered root module (JSON), module versions, backend config, plan JSON, secret references (not values) |
| Observed | GCS LOB bucket `…/<tenant>/terraform.tfstate` + Postgres `resource_instances` summary | Run (apply, refresh) + post-build | Terraform state; resource ids, outputs (non-secret), post-build receipts, last-observed timestamp |

Requirements:
- SSP-PROD-010 A state transition MUST be recorded as an immutable event (`order_events`) with actor, timestamp, reason and correlation ids (order, run, workflow).
- SSP-PROD-011 Requested and Approved MUST NOT contain secret values. Fields marked `secret: true` in the request schema are accepted only as Secret Manager references, or generated by the platform after approval.
- SSP-PROD-012 Approved specs are immutable. A change to a live resource is a new order of kind `change` referencing the resource instance; a delete is an order of kind `decommission`.
- SSP-PROD-013 Drift is a sub-state of Observed and MUST NOT move the resource out of Observed; it is cleared by a reconcile run or by an explicit `adopt` order.

## 3. Approval rules

- SSP-PROD-020 Approval is computed by code: validate against request schema → apply guardrails from the ServiceSpec (inject / deny / warn) → evaluate request-stage OPA policy → compute price estimate → check tenant quotas and APM budget → produce the approved spec.
- SSP-PROD-021 Auto-approve when: policy result is `allow`, no guardrail returned `deny`, estimate within APM monthly budget headroom, and the change-management mapping requires no CR.
- SSP-PROD-022 Require a **ServiceNow change request** when the tenant boundary is production and the change class mapping (B-0002) says so (initially: any `change` or `decommission` in production; `create` in production is a standard change recorded automatically). The order waits in Approved with `gate: cr_pending` and continues when the CR is approved (polled or webhook).
- SSP-PROD-023 Require **owner sign-off** for `decommission` of any resource holding data (ServiceSpec `lifecycle.holdsData: true`) and for `change` orders that the ServiceSpec marks `ownerSignoff: true`.
- SSP-PROD-024 Policy `deny` rejects the order with the rule ids and a human-readable reason; `warn` is shown in the receipt and recorded.

## 4. Defaults from context (APM-ID-driven)

- SSP-PROD-030 When a buyer selects a delivery destination, the platform loads the APM record (tier, data classification, cost center, LOB) and applies ServiceSpec `derive` rules before the form is shown. Example: Tier 1 database → multi-region / active-active; PHI → CMEK + retention lock + private access only.
- SSP-PROD-031 Derived fields are shown read-only with the rule that set them and the requirement id, and can be relaxed only if the ServiceSpec marks them `relaxable` (then a `warn` and owner sign-off apply).

## 5. Order journeys (buyer)

1. **Browse**: storefront home shows frequent SKUs for the buyer's history and LOB, delivery destinations grouped by cloud, recently viewed, saved drafts. Search (top-center) finds SKUs, destinations, orders and resources by id or name. (SSP-PROD-040)
2. **Configure & Buy**: multi-step checkout generated from the request schema and `ui.yaml`; a sticky Order Summary shows itemized estimate, injected guardrails, policy warnings and a **View as code** tab (Terraform and CLI). (SSP-PROD-041, SSP-PROD-042)
3. **Preflight**: every edit debounced to `POST /v1/orders/preflight`; the receipt is always the server's view. (SSP-PROD-043)
4. **Place order**: `POST /v1/orders` with the preview hash; mismatch → 409 and the UI refreshes the receipt. (SSP-PROD-044)
5. **Track**: order page streams events (SSE) through Requested → Observed, including run logs (redacted) and post-build receipts; estimated time remaining from historical percentiles for the service. (SSP-PROD-045)
6. **Operate**: resource page shows observed attributes, drift, cost to date (if available), and actions: change, decommission, re-run post-build, export code. (SSP-PROD-046)
7. **Ask Sidekick**: at any point, open the concierge; it can prefill a checkout, explain a guardrail or policy denial with citations, or report status. It never places an order without the same confirmation card. (SSP-PROD-047; see `17-conversational-provisioning-spec.md`)

## 6. Desired set and reconciliation (how Expected is produced)

Because there is exactly one state file per tenant boundary (D-08), the platform maintains a **desired set** per tenant boundary and renders it to a single root module.

- SSP-PROD-050 Each tenant boundary has one long-running Temporal entity workflow `TenantReconciler(tenant_id)` that owns the lock on that boundary's state and processes a FIFO queue of approved specs (signals).
- SSP-PROD-051 On each cycle the reconciler renders `main.tf.json` with one `module` block per resource instance in the desired set, pinning each to its approved module version, plus provider and backend blocks, and writes it to `…/<tenant>/expected/<generation>/`.
- SSP-PROD-052 The reconciler batches queued specs that arrived within a configurable window (default 20 s) into one run, except specs with `isolation: true` (e.g., decommission), which run alone.
- SSP-PROD-053 A run is `plan` → plan-stage policy → `apply` only if the plan touches exactly the resource instances in the batch (the plan gate); any unexpected destroy/replace fails the run and raises an operator alert.
- SSP-PROD-054 Module upgrades are separate orders of kind `upgrade` created by the Release process in **waves** (canary tenants → one LOB → all), each wave gated by the plan gate and a soak period.
- SSP-PROD-055 Per-tenant concurrency is 1 run at a time; the queue depth and age are exposed as metrics and shown in the control room. Fairness across tenants is provided by Temporal task queues per LOB with equal worker allocation.

## 7. Drift

- SSP-PROD-060 A scheduled `DriftScan(tenant_id)` (default every 6 h, and after any run) performs `terraform plan -refresh-only` and classifies drift per resource instance: `benign` (allowlisted attributes), `config` (platform-managed attribute changed), `missing` (resource gone), `unmanaged` (new resource in the boundary not in the desired set, from cloud asset inventory).
- SSP-PROD-061 Default response: record, notify buyer and operator, show on resource and control room; **no automatic revert** in Phase 1. Per-service `drift.autoRevert: true` enables reconcile for `config` drift after a grace period.
- SSP-PROD-062 Break-glass: an operator can mark a tenant `break_glass` for a window; drift during the window is recorded with the incident reference and excluded from auto-revert.

## 8. Decommission

- SSP-PROD-070 Decommission is an order of kind `decommission`; the ServiceSpec defines `lifecycle.delete.mode: soft|hard` and `retentionDays`. Soft delete first disables/locks, then removes from the desired set after retention; hard delete removes immediately after required sign-offs.
- SSP-PROD-071 Decommission in production always requires owner sign-off and, per B-0002, a CR.
- SSP-PROD-072 Orphan cleanup: `unmanaged` drift older than 30 days raises an `adopt or remove` task to the app owner.

## 9. Post-build

- SSP-PROD-080 Post-build steps are declared per service (`postBuild: [...]`) and executed by the `PostBuild` child workflow after apply: CMDB registration, backup enrolment, monitoring onboarding, team notification, DNS (Infoblox), firewall requests. Each step is an activity with its own idempotency key and receipt.
- SSP-PROD-081 A failed post-build step does not roll back the resource; the order shows `Observed (post-build incomplete)` and the step is retried with backoff, then escalated to the owning agent team's queue.

## 10. Status, notifications, monitoring

- SSP-PROD-090 Buyers receive notifications (email + optional Teams/Slack webhook) on: order placed, approved, waiting on CR/sign-off, delivered, failed, drift detected.
- SSP-PROD-091 The order page and the control room read the same event stream; there is no separate "status" store.
- SSP-PROD-092 Platform SLOs (initial): order → Approved p95 < 60 s when no CR; Approved → Observed p95 < 20 min for Phase 1 services; API availability 99.9 %; capacity target 10–20 provisions/day in Phase 1, designed for 500/day.

## 11. Security and audit

- SSP-PROD-100 AuthN: OIDC from the corporate IdP; the API accepts JWTs issued through the API gateway (API Forge / Apigee) and verifies issuer, audience and expiry. Service-to-service calls use GKE Workload Identity.
- SSP-PROD-101 AuthZ: persona + entitlement checks in the API; field-level rules from the ServiceSpec (`ops_only` fields are hidden and rejected for buyers).
- SSP-PROD-102 Every API write, workflow decision, run and post-build receipt is an audit event with actor, subject, before/after hashes; events are exported to the SIEM.
- SSP-PROD-103 The Platform SA can be disabled from the control room in one action (kill switch); reconcilers detect the disabled state and pause.
- SSP-PROD-104 Runs never receive long-lived credentials: Workload Identity → Platform SA → short-lived impersonated token for the tenant SA, scoped to the run's lifetime.

## 12. Multi-cloud sequencing

GCP first (control plane and first services), AWS second (per-OU host account pending Security), Azure third. The ServiceSpec, API and UI are cloud-neutral from day one; only `ssp-module-*` repos and the runner's provider configuration are cloud-specific.

## 13. Out of scope for Phase 1

Legacy 1.0 import (handled by `ssp-migrate`, Phase 2), AWS/Azure execution, auto-revert of drift, cost actuals (estimates only), customer-defined approval chains.
